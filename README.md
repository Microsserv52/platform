There is no Cart service. The Store keeps its cart in browser storage, Redis is provisioned as a shared endpoint with `CACHE_ENABLED=false`, and no service-level caching exists. The Store PWA is online-only.

Terraform provisions the AWS environment: VPC, EKS with 2–6 `t3.medium` nodes, ECR, RDS PostgreSQL, ElastiCache Redis, private S3 buckets and CloudFront. Product implements image persistence with the AWS SDK for Java v2; Compose still uses the local blob-storage mock. CloudFront delivers product images. The deployed inventory is recorded in [delivery evidence](docs/project/delivery.md).

Observability is self-hosted with Prometheus, Mimir, Loki, Tempo, Pyroscope, Graphite, Telegraf, Grafana, Alloy and blackbox, with eight dashboards and unified alerts. Services use OpenTelemetry and the frontends use Faro. The same stack runs on EKS; Grafana Cloud is optional and not required. Edge protection uses AWS Shield Standard, CloudFront and security groups; an AWS WAF managed-rule web ACL is prepared but not attached. No Kafka broker or client is implemented.

Architecture details: [Observability](docs/operations/observability.md), [Grafana on AWS](docs/operations/grafana-aws.md), [AWS assessment](docs/infrastructure/aws-observability-assessment.md), [Cart service](docs/services/cart/index.md), [Asynchronous events](docs/project/asynchronous-events.md) and [AWS edge security](docs/infrastructure/aws-edge-security.md). There is no custom domain; see [custom domains](docs/infrastructure/custom-domains.md).

Web application that allows authenticated users to buy and sell products
through a set of microservices.

## Web applications and local preview

The [frontend documentation](docs/frontend/overview.md) covers three
independent Next.js applications integrated as Git submodules: `web/landing` at
`/`, `web/store` at `/store`, and `web/admin` at `/admin`, on one domain.
The agreed UI is English, with a shared modern brand and a public catalog.

This is an **educational mock store: no real payments or transactions take
place, and no goods are shipped**. Authenticated users create persisted
demo orders. The store includes an online-only PWA manifest; Grafana Faro and
Umami are integrated; production collection values are not configured. Each app
exports static files and has a Dockerfile. CloudFront serves the static exports
with per-app build values; frontends are not Kubernetes workloads.

To test the frontend independently of the missing Product/Exchange images:

```bash
docker compose -f compose.frontend-demo.yml up --build -d
```

Open `http://localhost:8081/`, `/store/` or `/admin/`. This separate local-only
mode visibly labels disposable API fixtures. See the [local testing guide](docs/frontend/delivery.md)
for fixture inputs, real-service mode and verification limits.

## Staging environment

The [staging environment](docs/infrastructure/staging.md) is defined in
`terraform/environments/staging` and `k8s/overlays/staging`. It is a dedicated
VPC and EKS cluster with one replica per service, private RDS, ElastiCache and S3,
and a separate observability stack. It has no public edge; access goes through
the EKS endpoint and `kubectl port-forward`. No CI/CD workflow provisions or
deploys it.

## Which environment should I run?

| Environment    | Purpose                                   | Database                          | Exchange provider                   | Entry point                      |
| -------------- | ----------------------------------------- | --------------------------------- | ----------------------------------- | -------------------------------- |
| Docker Compose | Local development and integration testing | PostgreSQL container              | Local deterministic mock by default | `http://localhost:8080`          |
| LocalStack     | AWS deployment rehearsal                  | LocalStack RDS                    | Local exchange mock by default      | LocalStack CloudFront/gateway     |
| MicroK8s       | Local Kubernetes validation               | `k8s/overlays/microk8s/database.yaml` | External Exchange service URL   | Ingress address                  |
| AWS EKS        | Production backend                        | RDS PostgreSQL                    | External Exchange service URL       | Production Ingress/load balancer |
| AWS EKS staging | Developer acceptance, one replica         | Private RDS PostgreSQL            | Staging sandbox or adapter          | EKS endpoint + port-forward      |

Compose and Kubernetes are separate runtime environments. Do not use the
Compose mock or its local defaults in EKS.

### Run local Compose

```bash
cp .env.example .env
docker compose up --build -d
docker compose ps
docker compose down
```

Product and Exchange are checked out as submodules at `api/product` and
`api/exchange`; Compose builds their images from this checkout. Compose also
supplies PostgreSQL and the local Exchange provider mock.

> [!WARNING]
> `.env.example` is a local-only starting point and its placeholder values are
> unsafe. Replace at minimum `POSTGRES_PASSWORD`, `JWT_SECRET` and
> `INTERNAL_SERVICE_SECRET` before exposing this stack. `JWT_SECRET` is
> validated by Gateway, Auth, Account, Order, Product and Exchange and must be
> identical for all of them. Product shares the local PostgreSQL database
> (`POSTGRES_DB`, default `platform`); Flyway creates its tables on first
> startup. The local Compose fallback also seeds a LOCAL-ONLY admin
> (`admin@microsserv52.com` / `1berto52`) through `ADMIN_EMAIL`/`ADMIN_PASSWORD`;
> `.env.example` leaves both empty and the bootstrap refuses to run in
> production (`ENV`/`APP_ENV`/`SPRING_PROFILES_ACTIVE`). Never use these
> defaults for MicroK8s or EKS.

Optional demo data (20 products with pictures, a demo customer, and orders)
through the real APIs:

```bash
docker compose --profile demo up --abort-on-container-exit demo-seeder
```

See [Get started → Demo data](docs/development/get_started.md#demo-data-optional).

### Run local MicroK8s

Follow the [Kubernetes runbook](k8s/README.md). It requires MicroK8s with the
Nginx ingress addon, a `platform-secrets` Secret, reachable Product/Exchange
services, and local images (including `microsserv52-image-storage:local`) loaded
into MicroK8s.

### Run the LocalStack rehearsal

Run `scripts/localstack-up.sh` with a LocalStack Student token in `.env`. It
provisions EKS, ECR, RDS, ElastiCache, S3 and CloudFront through Terraform and
deploys the backend. See [LocalStack rehearsal](docs/infrastructure/localstack.md)
and the [LocalStack runbook](docs/infrastructure/runbook.md#localstack-rehearsal).

### Run production EKS

Log in with a short-lived AWS profile, optionally set `TF_STATE_BUCKET`, then run
`scripts/deploy-aws.sh --frontends`. The script applies Terraform, pushes images,
creates the cluster secret and deploys the `aws` overlay. A manual
**Publish EKS images** workflow builds and pushes images to ECR; deployment
remains shell-first. See the [AWS deployment runbook](docs/infrastructure/runbook.md#aws-deployment),
[Kubernetes](k8s/README.md), [Terraform](terraform/README.md) and
[Deployment](docs/infrastructure/deployment.md).

## CI/CD and environment variables

Each service repository owns lint, format, tests, JaCoCo quality gates, CodeQL,
and container publishing to GHCR. Images are tagged
`ghcr.io/microsserv52/<service>:sha-<commit>`. The platform workflow validates
the integration and pulls the image for each submodule commit; it builds locally
only when that immutable image is not available. AWS provisioning and deployment
run from a logged-in shell; the separate **Publish EKS images** workflow only
builds and pushes ECR images.

Copy [`.env.example`](.env.example) for local development. Do not commit the
real `.env` file or any secret values.

Configure repository secrets in **Settings → Secrets and variables → Actions**
for each repository:

| Repository                   | Required secrets                                                                                                                                                                                         |
| ---------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Microsserv52/platform`      | `AWS_REGION`, `AWS_DEPLOY_ROLE_ARN` for the manual ECR image publish workflow. Deployment itself runs from a logged-in shell; see [`terraform/README.md`](terraform/README.md).                           |
| `Microsserv52/account`       | `JWT_SECRET`, `INTERNAL_SERVICE_SECRET`, `SPRING_DATASOURCE_URL`, `SPRING_DATASOURCE_USERNAME`, `SPRING_DATASOURCE_PASSWORD`                                                                             |
| `Microsserv52/auth`          | `JWT_SECRET`, `INTERNAL_SERVICE_SECRET`, `ACCOUNT_URL`, `ACCESS_TOKEN_EXPIRATION_SECONDS`                                                                                                                |
| `Microsserv52/gateway`       | `JWT_SECRET`, `AUTH_URL`, `ACCOUNT_URL`, `ORDER_URL`, `PRODUCT_URL`, `EXCHANGE_URL`                                                                                                                      |
| `Microsserv52/order-service` | `JWT_SECRET`, `SPRING_DATASOURCE_URL`, `SPRING_DATASOURCE_USERNAME`, `SPRING_DATASOURCE_PASSWORD`, `PRODUCT_URL`                                                                                         |
| `Microsserv52/product`       | `JWT_SECRET`, `SPRING_DATASOURCE_URL`, `SPRING_DATASOURCE_USERNAME`, `SPRING_DATASOURCE_PASSWORD`                                                                                                        |
| `Microsserv52/exchange`      | `JWT_SECRET`, `EXCHANGE_PROVIDER_URL`, `EXCHANGE_PROVIDER_API_KEY`                                                                                                                                        |
| `Microsserv52/order`         | No runtime secrets; this repository contains the reusable API contract.                                                                                                                                  |

For local Compose, copy `.env.example` to `.env`; Compose provisions the local
PostgreSQL database and defaults internal service settings. Product uses the
same local PostgreSQL database and the shared `JWT_SECRET` (its Flyway
migrations create its schema on first boot). Product and Exchange images plus
Exchange provider settings are the only external local inputs. For MicroK8s,
create `platform-secrets` as described in [`k8s/README.md`](k8s/README.md).
For the AWS-like rehearsal, run `scripts/localstack-up.sh` (see
[`docs/infrastructure/localstack.md`](docs/infrastructure/localstack.md)).
For real AWS, log in with a short-lived profile and run
`scripts/deploy-aws.sh`; Terraform provisions VPC, EKS, ECR, RDS, ElastiCache,
S3 and CloudFront. Deployment is intentionally not wired to CI/CD.

### Environment variable locations

| Variable type                | Daily Compose              | LocalStack rehearsal                        | AWS deployment                              |
| ---------------------------- | -------------------------- | ------------------------------------------- | ------------------------------------------- |
| Service URLs and image tags  | Root `.env`                | Terraform outputs + ConfigMap patches       | Terraform outputs + ConfigMap patches       |
| JWT and internal credentials | Root `.env` (never commit) | `platform-secrets`                          | `platform-secrets`                          |
| Database URL and credentials | Root `.env`                | LocalStack RDS output                       | RDS output (local Terraform state or S3)    |
| AWS deployment values        | Not required               | Dummy `AWS_ACCESS_KEY_ID=test` (LocalStack) | `AWS_PROFILE` session; no long-lived keys   |
| LocalStack licence           | Not required               | `LOCALSTACK_AUTH_TOKEN` in `.env`           | Not required                                |

The service workflows need `packages: write` to publish GHCR images. Keep GHCR
packages private unless the deployment policy explicitly requires public
images.
